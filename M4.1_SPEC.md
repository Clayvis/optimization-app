# M4.1_SPEC.md

AI Schedule Optimizer. Post-v1.0 polish phase. Adds Claude-driven schedule **generation** from user goals + constraints to complement the **adaptation** loop already shipped in M3.7 (CoachService.suggestScheduleOptimizations). Resolves the gap surfaced after wife-onboarding live testing: the four bundled template JSONs (balanced / gym / language / fasting) are still one-size-fits-most; the user needs a personalized starting schedule that respects their stated goals, available windows, and injury constraints.

Numbering note: M3.8 and M4 are tagged complete. This phase slots between M4 (v1.0 ship) and v1.5+ deferred work. Called M4.1 to make the lineage explicit.

---

## Vision

A new user (Clay's wife, buddy, future App Store testers) describes their week in their own words plus a short structured intake. Claude returns a complete weekly schedule. The user reviews the whole proposal, accepts it (or per-block edits), and lands on TodayView with their data, not Clay's.

Over the next 2-4 weeks, the existing M3.7 adaptation loop watches what they actually do and proposes specific reorderings. Memory of rejected proposals means the same bad suggestion never comes back twice. Identity-framed copy throughout. Per-change accept/reject preserves autonomy.

For Clay this is the same flow, with the option to skip generation and load his existing schedule from CloudKit.

---

## Why now

Research findings (synthesized in `~/.claude/plans/dont-create-seperate-branched-moonlit-hammock-agent-*.md`):

- **Implementation intentions outperform reminders** (Sheeran et al. meta-analysis, d = .27–.66, n = 642 tests). The AI must anchor blocks to triggers when the user provides them ("after kid drop-off", "after coffee"), not invent fake anchors.
- **Fresh-start effect on week boundaries** (Dai/Milkman 2014, n ≈ 66K). The existing adaptation pass running on Sundays is aligned; do not move to continuous reflow.
- **Autonomy-supportive UX** (Ntoumanis 2021, 73-intervention meta-analysis). Per-change accept/reject, asset framing, never auto-apply.
- **Avoid "calendar anxiety"** (documented Motion failure mode, 11 reshuffles in a day reported by users). Generation is one-shot; adaptation is opt-in weekly. No mid-week rewrites.
- **Memory of rejected slots is a gap nobody fills** in the competitor landscape (Reclaim, Motion, Trevor, SkedPal surveyed). CoachMemoryService already exists; wiring rejection memory into it is a small lift with high differentiation.

## What's already built (do not rebuild)

M3.7 shipped:

- `ClaudeAPIClient` (URLSession, keychain-backed key, retry) — `Services/ClaudeAPIClient.swift`
- `CoachService.suggestScheduleOptimizations(lookbackDays:)` — pattern-driven adaptation
- `CoachService.generateWeeklyProgrammingPass` — Sunday weekly program (volume distribution, not block-by-block)
- `CoachService.prescribeTodaysWorkout` — daily workout prescription
- `ScheduleSuggestion` model + `ScheduleSuggestionInbox` view + accept flow
- `WeeklyProgram` model + `WeeklyProgramCard` view
- `CoachContextV2` (historical context for prompts)
- `CoachMemoryService` (key-value memory store with importance + expiry)
- `CoachPrompts` (locked system prompts per generation mode, motivationStyle-aware)
- `TrendAnalyticsService.patternsDetected(over:minConfidence:)` (pre-computed pattern flags)

M3.7 did NOT ship:

- **Schedule generation from scratch.** No code path takes "goals + constraints in natural language" → full weekly ScheduleBlock array. Today's only options are the four static template JSONs from the chooser.
- **Rejected-proposal memory.** Dismissing a ScheduleSuggestion just sets status=dismissed. The CoachService doesn't read those dismissals back into prompts, so the same suggestion can re-surface next week.
- **Diff-vs-current preview.** ScheduleSuggestionInbox shows one suggestion at a time as a card; there's no "here's your current week, here's what would change" comparison view.
- **Trigger-anchored authoring.** Existing seed JSONs and suggested changes use absolute clock times. No code asks for or stores user-defined trigger events (e.g., `after_kid_dropoff`).

M4.1 fills exactly those four gaps.

## Architecture

### Generation pipeline (new)

```
ScheduleGenerationView (form: goals, constraints, anchors, training prefs)
        │
        ▼
ScheduleAIService.generate(intake:) async throws -> GenerationProposal
        │
        ├─ Build system prompt from CoachPrompts.system(.generateSchedule, style:)
        ├─ Build user prompt: intake + module vocabulary + hard constraints
        ├─ Call ClaudeAPIClient with output_config.format (JSON Schema)
        ├─ Decode response → [ScheduleBlockDraft]
        ├─ ScheduleValidator.validate(drafts, against: intake)
        │     └─ On failure: ONE retry with error feedback as user turn
        └─ Return GenerationProposal { drafts, warnings, rationale }
        │
        ▼
ScheduleDiffView (proposal preview; user accepts whole or edits blocks)
        │
        ▼
ScheduleSeed.applyDrafts(_:modelContext:) — wipes non-custom, inserts drafts
```

Output JSON Schema (concrete contract Claude returns):

```json
{
  "blocks": [
    {
      "dayOfWeek": 1,
      "startTime": "18:00",
      "endTime": "19:00",
      "activity": "Lift A",
      "type": "training",
      "module": "lift_a",
      "anchorEvent": "after_kid_dropoff",   // null when clock-time only
      "anchorOffsetMinutes": 30             // null when no anchor
    }
  ],
  "rationale": "string, max 280 chars, identity-framed",
  "warnings": ["string"]                    // soft notes for the user
}
```

`anchorEvent` and `anchorOffsetMinutes` are new fields on `ScheduleBlock` (additive, schema bump to V9; lightweight migration). They are display-only at first — TodayView shows "Lift A — 30 min after drop-off" when set. Time math still uses startTime/endTime so the existing fasting, hydration, streak engines need no changes.

### Adaptation extensions (existing path)

```
WeeklyReviewView (existing ScheduleSuggestionInbox, extended)
        │
        ▼
Suggestion card with three actions:
  [Accept]    → ScheduleSuggestion.status = accepted → apply change
  [Snooze]    → ScheduleSuggestion.snoozedUntil = +7 days
  [Dismiss]   → ScheduleSuggestion.status = dismissed
                + CoachMemoryService.add(
                    key: "rejected_suggestion_<hash>",
                    value: "<one-line summary>",
                    importance: 2,
                    expiresIn: 60 days
                  )
        │
        ▼
Next time CoachService.suggestScheduleOptimizations runs,
gatherFullContext includes rejected-proposal memory in the user
prompt under <rejected_proposals> so Claude does not re-suggest.
```

The CoachPrompts.suggestSchedule system prompt is extended with one paragraph: "Before proposing, check `<rejected_proposals>`. Do not propose any change semantically equivalent to a rejected one."

### Validator (new)

`ScheduleValidator` is pure-Swift, no I/O. Checks:

1. **Overlap on same day** — two blocks with intersecting [startTime, endTime] on same `dayOfWeek`.
2. **Sleep window non-intersection** — no block crosses `userProfile.fastWindowStartHour` ± user sleep override.
3. **Weekly volume cap** — count blocks where `module IN (lift_a, lift_b)` per week, fail if > 6.
4. **Module vocabulary** — `module` must be in known set or null.
5. **Anchor event vocabulary** — `anchorEvent` must be in the user's declared anchor list (from intake) or null.
6. **Day-of-week enum** — `dayOfWeek IN [1..7]`.

Failures produce a typed `ScheduleValidationError` with the offending block index. Used twice: gating the API response (retry loop) and gating the user's manual edits in the diff view (warning banner, not block).

## Data model changes

### New fields on existing models

`ScheduleBlock` (additive, SchemaV9):

```swift
var anchorEvent: String?            // "after_kid_dropoff" | "after_coffee" | "after_dinner" | "before_bed" | nil
var anchorOffsetMinutes: Int?       // signed: -15 = 15 min before, +30 = 30 min after; nil when no anchor
```

`UserProfile` (additive, SchemaV9):

```swift
var anchorEventsCSV: String = ""    // user-declared anchor labels, comma-separated, e.g. "after_kid_dropoff,after_dinner"
var lastGeneratedAt: Date?          // timestamp of last AI generation; surfaces "regenerate" cooldown UX
```

### New model

```swift
@Model final class ScheduleGenerationRun {
    var generatedAt: Date = Date.distantPast
    var modelUsed: String = ""              // e.g. "claude-opus-4-7"
    var intakeJSON: String = ""             // captured intake form values, for replay/debug
    var proposalJSON: String = ""           // full GenerationProposal payload
    var statusRaw: String = "proposed"      // "proposed" | "accepted" | "discarded"
    var tokenUsage: Int = 0
    var costEstimateCents: Int = 0          // for "AI calls this month" surface (M4.1 stretch)
}
```

Persisted so the user can revisit a discarded proposal ("oh wait, that one was actually fine"). Auto-purged after 30 days.

### Schema bump

SchemaV9 = SchemaV8 + new ScheduleBlock fields + new UserProfile fields + ScheduleGenerationRun. Lightweight migration. Anchor fields default nil; anchorEventsCSV defaults "".

## Prompts

System prompt for generation (`CoachPrompts.system(.generateSchedule, style:, customStylePrompt:)`):

```
<role>You are a scheduling engine for a single-user habit-tracking app. You emit ScheduleBlock data — not motivation, not commentary. The user reviews everything before it lands in their schedule.</role>

<design_principles priority="hard">
  <principle>Implementation intentions over clock times. When the user provides an anchor event, set anchorEvent + anchorOffsetMinutes on the block.</principle>
  <principle>Identity framing in activity labels. "Lift A", "Japanese study", "Evening walk". Never "Crush legs", "Level up", "Get after it".</principle>
  <principle>One behavior per block. No "lift + study" stacked blocks.</principle>
  <principle>Recovery is a real block. Schedule rest explicitly when the user's training cadence implies it.</principle>
  <principle>Plain language. No emojis. No exclamation points. No motivational verbs.</principle>
</design_principles>

<hard_constraints>
  <constraint>Module vocabulary: lift_a, lift_b, basketball, swim, japanese, guitar. Others must be null.</constraint>
  <constraint>Type vocabulary: training, learning, study, admin, recovery, transit, other.</constraint>
  <constraint>Day encoding: 1=Mon ... 7=Sun (ISO 8601).</constraint>
  <constraint>Time format: HH:mm, 24-hour, 00:00-23:59.</constraint>
  <constraint>No block may cross the user's declared sleep window.</constraint>
  <constraint>Honor every constraint provided in the user's intake. Treat injury and time-block locks as inviolable.</constraint>
</hard_constraints>

<soft_preferences>
  <preference>Respect the user's stated training cadence (e.g., "3 lifts per week"). Do not exceed.</preference>
  <preference>Place cognitively demanding work at the user's stated peak alertness window.</preference>
  <preference>If the user provides anchor events, prefer trigger-anchored authoring.</preference>
</soft_preferences>

<user_profile>
  {{ cached: name, motivationStyle, equipmentAccess, primaryGoal, secondaryGoals, anchorEvents, restrictions }}
</user_profile>

<rejected_proposals>
  {{ from CoachMemoryService, key prefix "rejected_suggestion_" }}
  {{ empty on first generation; populated on subsequent adapt runs }}
</rejected_proposals>

Output: a JSON object matching the response schema. Do not include prose outside the JSON.
```

User prompt for generation is just the intake form values rendered as a structured block plus a one-paragraph free-text "anything else you want me to know" field.

System prompt for adaptation already exists in CoachPrompts.suggestSchedule. M4.1 adds one paragraph and the `<rejected_proposals>` block injection point.

## UX

### Onboarding integration

The schedule step in `OnboardingView` currently shows five static template tiles. M4.1 adds a sixth tile at the top:

```
┌─────────────────────────────────────┐
│  ✨ Build me a schedule (AI)        │
│  Tell me your goals; I'll draft a   │
│  week. You review before it lands.  │
└─────────────────────────────────────┘
[Balanced] [Gym focused] [Language focused] [Fasting focused] [Blank]
```

Tapping it pushes `ScheduleGenerationView`. Returns to onboarding wrap-up on accept; user can still back out and pick a static template.

### Settings entry

Settings → Schedule → "Generate with AI" button. Same path as onboarding. Surfaces `lastGeneratedAt` and a soft cooldown ("you generated 2 days ago; sure you want a fresh draft?").

### Generation form (`ScheduleGenerationView`)

Three-section form, ~10 fields max:

1. **Goals.** Primary goal picker (4 chips: strength, endurance, skill-building, fasting-priority) + free-text "What does a great week look like for you?" textarea.
2. **Constraints.** Days available toggles (Mon-Sun). Earliest/latest training time steppers. Sleep window. Injuries CSV.
3. **Anchors (optional, collapsed).** "If your day has predictable anchors, list them so blocks can ride along." Examples shown as chips: "after kid drop-off", "after coffee", "after work", "after dinner". User can add custom.

Bottom: "Generate" button. Disabled until primary goal selected.

### Diff preview (`ScheduleDiffView`)

Side-by-side or stacked (depending on screen width) showing current week vs proposed week. Each block is taggable:

- New blocks have a green + indicator.
- Removed blocks have a red − indicator.
- Modified blocks (same module, different time) have a yellow → indicator.
- Identical blocks dim to 40% opacity.

Footer actions:

- **Apply all** (primary CTA, identity-framed: "This is my week.")
- **Edit per block** (pushes into a list view; tap a block to inline-edit time/day; warnings if validator complains)
- **Discard** (destructive; logs the run as ScheduleGenerationRun.status = discarded)

### Adaptation extension (`ScheduleSuggestionInbox`)

Existing inbox is functional. M4.1 adds:

- A "Why this?" disclosure that reveals the pattern data backing the suggestion (already stored as `rationaleData` on the model; just surface it).
- A "Dismiss" button (renamed from existing "Discard" if present) that writes a `CoachMemory` row keyed by the suggestion's change signature, so it won't re-surface.
- A one-line summary at the top of the inbox: "3 suggestions ready" or "no suggestions this week — your pattern is steady."

## Definition of Done

- All 18 PLAN tasks complete, tests passing.
- New user can complete onboarding via the AI path and land on TodayView with a schedule reflecting their stated goals.
- Existing user can re-trigger generation from Settings without losing custom blocks (isCustom == true preserved).
- Generated blocks with `anchorEvent` set render correctly in TodayView ("Lift A — 30 min after drop-off").
- Validator catches all six failure classes (overlap, sleep, volume, module vocab, anchor vocab, weekday).
- Retry-on-validation-fail succeeds at least 90% of the time in dev testing (instrument with logger.info).
- Dismissed suggestions write to CoachMemoryService and the next `suggestScheduleOptimizations` call includes them in the prompt.
- ScheduleGenerationRun rows persist; user can view "AI calls this month" in Settings → Diagnostics.
- Build clean on iOS + watchOS, zero warnings.
- All 379+ existing tests still pass; 20+ new tests for M4.1.
- PR merged to main (per project workflow: direct push to main, no per-task branches), tag `m4.1-complete` pushed.

## Performance Benchmarks

- `ScheduleAIService.generate` cold path (Opus 4.7 with thinking, no cache): < 15 s.
- `ScheduleAIService.generate` warm path (prompt cache hit on system prompt): < 8 s.
- `ScheduleValidator.validate` for a 14-block week: < 5 ms.
- `ScheduleDiffView` first render with full week (existing + proposed): < 500 ms.
- `CoachMemoryService.active` query with 100 rejected-proposal rows: < 50 ms.

## Out of scope

- Continuous mid-week reflow. Generation is one-shot; adaptation is weekly. No exceptions.
- Chronotype inference from log data. Ask once via µMCTQ in the intake form if the user doesn't pick a peak window; do not try to learn it.
- Auto-apply of any AI-authored change without user accept.
- Schedule generation for the watch target. Watch reads CloudKit-synced blocks; iOS authors them.
- "Conversational" generation (multi-turn chat with Claude). The intake form is structured. Future v1.5 could add chat refinement.
- Goal recommendation (Claude doesn't suggest goals; user states them).
- Multi-user shared schedules (Partner Mode is a separate Tier 2 feature; M4.1 stays single-user).
